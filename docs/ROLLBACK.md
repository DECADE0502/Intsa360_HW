# Insta360 硬件提效平台回滚与恢复说明

## v3 更新模型

平台更新不会直接覆盖正在运行的版本。每个版本都作为独立运行时存放在安装目录的 `runtime\<版本+修订>` 下，新旧运行时可以并列存在。

安装根目录的 `installation.json` 是唯一活动版本指针，其中记录当前和上一个运行时。更新只有在新运行时校验通过后才会原子切换该指针，因此不会出现「半个新版覆盖半个旧版」。

## 自动恢复

更新在切换前会在安装根目录的 `.recovery\<任务编号>` 中建立受保护事务，记录旧指针、新指针和执行阶段。只要事务未完整提交，就不会把更新视为成功。

以下两个入口都会尝试恢复未完成事务：

- `Insta360_HW.exe` 启动器在启动后端前执行恢复。
- 安装时注册的开机恢复任务在用户登录后执行恢复。

恢复会根据事务阶段恢复 `installation.json` 指针、移除未提交的新运行时，然后重启上一个已验证版本。重复触发同一个已完成恢复不会再次破坏文件。

## 用户需要做什么

- **更新失败但平台可以打开**：关闭更新窗口，等待平台恢复到上一版后重启。保留 `%LOCALAPPDATA%\Insta360_HW\logs` 中的更新与启动日志。
- **平台无法启动**：再次运行当前版本 `Insta360_HW_Setup.exe` 并选择「修复」。Setup 会先处理未完成事务，再重建缺失的活动运行时。
- **安装指针或运行时已损坏**：使用同版本 Setup 的「修复」或「重装」，不要手工修改 `installation.json`。

## 回到旧版本

平台拒绝在线更新自动降级。直接运行比已安装版本更旧的 Setup 也不会默默覆盖新版。

如果经产品维护人员确认必须降级，请先导出重要业务数据，通过标准卸载器完整卸载当前版本，再运行目标旧版本的 Setup 安装。用户数据是否保留由卸载时的选项决定。

## 不要手工操作的内容

- 不要用 Git checkout、源码 ZIP 或文件复制覆盖安装目录。
- 不要删除或改写 `installation.json`、`.recovery` 和 `runtime` 中的任何内容。
- 不要在已安装的 v3 布局上运行根目录的遗留开发脚本。
