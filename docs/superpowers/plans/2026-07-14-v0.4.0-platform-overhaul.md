# Insta360 Hardware Efficiency Platform 0.4.0 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Deliver a single 0.4.0 release in which all six engineering tools, Cadence integration, plugin management, history, UI workflows, installation, OTA, repair, and uninstall are correct, consistent, and production-ready.

**Architecture:** Replace the monolithic stdlib HTTP application with a modular FastAPI/Uvicorn service while preserving old `/api/*` routes as adapters through 0.4.x. Store asset and run metadata in SQLite, keep file payloads on disk, isolate every tool engine and frontend feature, and replace the lifecycle implementation with prebuilt versioned runtimes and atomic activation.

**Tech Stack:** Python 3.11 embedded runtime, FastAPI, Uvicorn, Pydantic v2, SQLite, openpyxl, React 18, TypeScript, Ant Design 5, Lucide, IndexedDB, Vitest, React Testing Library, MSW, Playwright, PowerShell 5.1+, Inno Setup, Tcl compatible with OrCAD Capture 16.6 and 17.4.

## Global Constraints

- Target release is `0.4.0`; no public intermediate release is allowed.
- Target OS is Windows 10/11 x64; users install no development dependencies.
- Web UI copy is Chinese. Capture core menu labels remain ASCII English.
- Target computers never run npm, pip, Vite, TypeScript, or source builds.
- User data lives below `%LOCALAPPDATA%\Insta360_HW`; immutable runtimes live below `%ProgramFiles%\Insta360\HWAgent`.
- Every behavior change follows RED -> GREEN -> REFACTOR. A task is not complete until its focused tests and the relevant regression group pass.
- Agents may only edit their assigned paths. They must not revert or overwrite other agents' work.
- Shared aggregation files are owned only by integration tasks: `app/backend/api/app.py`, `app/backend/tool_registry.py`, `frontend/src/App.tsx`, `frontend/src/styles.css`, `HWAgent_Setup.iss`.
- Each task ends in one focused commit and reports files changed, tests run, results, and residual concerns.
- Release build and OTA payloads are prebuilt locally. GitHub is a validation and hosting layer, not a mandatory compiler.

## Per-Task Review Protocol

After each implementation commit:

1. A fresh spec reviewer checks only the task requirements and rejects missing or extra behavior.
2. The same implementer fixes spec gaps and the reviewer re-checks.
3. A fresh quality reviewer checks correctness, maintainability, security, tests, and path ownership.
4. The same implementer fixes quality findings and the reviewer re-checks.
5. The controller independently reads the diff, runs focused verification, and only then marks the task complete.

No task may be marked complete from an agent's report alone.
